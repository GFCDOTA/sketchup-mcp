sketchup-mcp

PDF de planta arquitetônica → um .skp do SketchUp fiel. Tudo — gates, testes, renders, o oráculo de decisão — existe pra provar que o modelo bate com o PDF.
consensus.json → build_plan_shell_skp → model.skp + renders + report → gates
Do PDF ao .skp, em 4 estágios

1 · Extrair

PDF → dados
Vetor do PDF vira consensus.json: paredes, aberturas, cômodos em pontos. Nada se inventa.

2 · Construir

dados → .skp
Python calcula a casca 2D; Ruby/SketchUp extruda e recorta janela (peitoril+verga).

3 · Validar

prova de fidelidade
Gates determinísticos (dados) + gate visual (olho/GPT) vs o PDF.

4 · Promover

runs → artifacts
Só o .skp aprovado vira o entregável versionado em artifacts/.
consensus.json ──▶ [Python] casca 2D ──▶ _shell_polygon.json ──▶ [Ruby/SketchUp] extruda+recorta ──▶ model.skp + report ──▶ [gates] determinístico + visual   │   a CI valida o lado Python ◀──┤──▶ SketchUp/olho valida o lado direito

Por que é organizado assim
A consensus é a fonte de verdade
Se uma parede/cômodo/abertura não está no consensus.json, ela não entra no .skp. Nada de geometria inventada pra "fechar" o número.
Cérebro (Python) ≠ músculo (SketchUp)
Python decide o quê construir; SketchUp constrói. A CI valida o cérebro (sem SketchUp); o olho + a VM validam o músculo.
O .skp é o entregável
Gates, testes e oráculo só contam se destravam um .skp provadamente fiel ao PDF. runs/ é scratch; só artifacts/ manda.
Decisão pelo oráculo, não pelo chat
Decisão técnica/merge vai pro gate :8765 e é respondida sozinha. Só o veredito visual é humano.
Replicável como template. A mesma espinha serve pra qualquer pipeline "entrada → artefato provado":
.claude/ (cérebro) · tools/ (motor) · fixtures/ → artifacts/ (entrada → entregável) · gates (prova) · .github/ (esteira) · CLAUDE.md (regras)
Troca o domínio (PDF→.skp) pelo teu, mantém a regra de ouro: uma fonte de verdade, o artefato como entregável, e a prova rodando sozinha.
